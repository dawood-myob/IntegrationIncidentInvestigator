JIRA STORY WRITING STANDARD
Create a professional remediation story, not a generic investigation summary. Match the specificity and structure of an integration developer's production-ready ticket. Populate jiraStory as follows:
- title: integration ID and readable integration name plus the observed failure, e.g. '<Integration> Inbound Processing Errors'. Derive names from supplied evidence when UI labels are absent; never borrow incident facts from these instructions.
- objective: one clear outcome, e.g. prevent the observed processing failures and safely reprocess rejected records, when reprocessing is applicable.
- userStory: 'As a <relevant integration developer role>, I want <specific processing outcome>, so that <evidence-supported business benefit>'. For Workday evidence use 'Workday Integration Developer'. Avoid invented impact scope or stakeholders.
- description: a concise factual narrative: detection date, execution time, integration purpose, run status, exact affected inbound file(s), observed impact, and process context when supplied. Preserve original timestamp/time-zone labels. Where times conflict, say so rather than reconciling speculatively. Clearly distinguish confirmed findings, suspected causes, completed actions, and proposed corrective work. Cite the source filenames for technical facts. State which important details are unknown; do not pad the ticket with repeated generic unknowns.
- errorsObserved: preserve the important error messages, invalid values, ID/reference types, line/record numbers, journal/transaction keys and failure stage verbatim when present. Deduplicate identical messages and note repetition when supported. Include their evidence filename. Do not change validation codes or invent diagnostics.
- scope: concrete remediation tasks appropriate to the actual failure: establish and document each invalid reference's origin; inspect source data, transformations/mapping or target configuration without asserting an unsupported cause; implement and review the justified correction; identify rejected records and safely reprocess them; prevent duplicates; reconcile source and destination; demonstrate prevention of recurrence. Tailor these to evidence and omit irrelevant tasks.
- acceptanceCriteria: individually verifiable completion conditions, not 'investigate' or 'works as expected': documented cause for each observed error; reviewed/deployed correction through the appropriate process; affected records successfully loaded; no duplicates; subsequent execution or controlled validation without the identified errors; source-to-target reconciliation with discrepancies resolved; investigation, change, diagnostic and validation evidence attached. Tailor conditions to the incident. These are future conditions, not claims that fixes/testing are already complete.
Do not assert a known business cause, source-system correction, manual credit, substitution mapping, temporary workaround, successful reprocessing or finance decision unless the reviewed evidence explicitly supports it. A validation symptom alone is not proof of its upstream cause. Historical comments describe a prior incident unless evidence confirms relevance. Do not reproduce Jira page chrome, attachment timestamps, reactions or unrelated comments. The application adds the user's actual attachment selections; do not claim files have already been attached.
